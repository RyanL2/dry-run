# C-0011 · /tmp snapshot copy dominates prepare · track: sandbox-perf · method: M-fixed-cost · status: partly supported
Observation: C-0003 found prepare takes 211 ms median. Prepare includes copying the user's own /tmp files, capped at 64 MiB (spike-0 design).
Hypothesis: The /tmp copy, not the workspace walk, drives prepare time on machines with busy /tmp dirs (pytest, pip caches).
Change: The same instrumented run as C-0009, with /tmp both empty and populated (5k small files). If supported, reuse a cached lower copy keyed on the /tmp fingerprint.
Prediction: Prepare time scales with /tmp contents: ≥ 100 ms more when /tmp is populated.
Disproof: Prepare time changes < 20 ms between empty and populated /tmp.
Budget: shared with C-0009.
Verdict: partly supported (ledger 2026-10-16 "stages", card C-0009..C-0011, both rows). With 5,000 small files under /tmp, median prepare rose from 239 ms to 360.5 ms (+121.5 ms), and tmp_snapshot from 0 ms to 120.5 ms, so the Prediction holds. The workspace walk (fp_pre 148.5 ms) still costs more than the copy, so "not the workspace walk" does not hold at this size. The copy stops at tmp max_entries (2000), so this cost is bounded. The cached /tmp lower is not built: it needs a decision on sharing one lower across runs, and on a cache key that does not walk /tmp again.
Follow-up (2026-10-16, branch feat/fingerprint-speedup; ledger rows "stages", card C-0009..C-0011): the copy cost is mostly mkdir, not file data. With pytest leftovers in /tmp (about 1,250 entries), 777 mkdirs took 270 of 405 ms (about 0.35 ms each on this ext4), and the bench's tmp_snapshot was 592 ms. A shared cached lower was rejected: concurrent runs would mount it at once, so it needs cross-process locking before it can be garbage-collected, and one bad copy would outlive its run. A hard-link farm was rejected too: nlink becomes visible in the sandbox, and it still pays every mkdir. Built instead: lend each new run the lower of one finished run and refresh it in place. A finished run is one whose sandbox has exited and whose extract, the last reader of the lower, is done. Each lower goes to exactly one run; a run that finds the slot empty copies from scratch. A copied file or symlink is kept only if (a) it was verified when made: the source had the same fingerprint from our stat until the whole read ended, and (b) the source has that fingerprint now. Under C-0009's fingerprint soundness, (a) means the copy is the content at that fingerprint, and (b) means the source has not changed since. Racy fingerprints never compare equal, so they are never reused. Everything else is removed and copied again. Directories get their modes and mtimes reapplied, and entries that are no longer selected (deleted, over a cap, owned by someone else, now excluded) are pruned. The refreshed tree equals a fresh copy, which a unit test checks. No new key is needed: the per-entry walk that selects entries also validates them, and walking 2,000 entries is cheap next to creating them. Result: tmp_snapshot 124.5 -> 13 ms with 5,000 files in /tmp (prepare 365.5 -> 173.5 ms), and 592 -> 94.5 ms with the pytest leftovers. Copies of changed files and new directories still cost what they did. Status: the cached lower is built, in the refresh form above.
