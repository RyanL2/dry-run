# C-0009 · full-tree fingerprint walks dominate fixed cost · track: sandbox-perf · method: M-fixed-cost · status: supported
Observation: C-0003 found fixed stages make up 87% of the 566 ms added latency on a 20k-file repo (prepare 211 ms, post-run 270 ms).
Hypothesis: The two full-tree lstat walks (before, and after for lower_changed) plus the upper extraction make up most of the fixed cost.
Change: Per-sub-stage timers (fingerprint pre/post, tmp snapshot, git snapshot, extract, git effects) over the C-0003 command set; shared run with C-0010 and C-0011.
Prediction: The two fingerprint walks together take ≥ 40% of fixed cost. Replacing the post-run walk with a check on changed dirs only (dir mtimes) cuts ≥ 100 ms.
Disproof: The fingerprint walks take < 20% of fixed cost.
Budget: 30 min CPU (the instrumented run is shared).
Verdict: supported (ledger 2026-10-16 "stages", card C-0009..C-0011, row with 1 file under /tmp). Median fixed cost 513.5 ms; the two walks are 75% of it (median per command): fp_pre 151 ms, fp_post 233.5 ms (the post walk also digests both trees). Prediction part 1 (>= 40%) holds. Part 2 (dir-mtime post check saves >= 100 ms) is untested: dir mtimes miss in-place edits of existing files, so lower_changed would lose concurrent modifications. That trade-off needs a decision before it is built.
Follow-up (2026-10-16, branch feat/fingerprint-speedup; ledger rows "stages", card C-0009..C-0011, commits 03a68a8 vs bae69e2): Part 2 is rejected, and so are its variants. (1) Dir mtimes miss in-place edits. (2) A post-run check of only the commit's targets and their parent entries adds nothing for clobbering: `dryrun apply` already re-checks every target's fingerprint (and every rmtree subtree digest) at commit time, which is later and therefore stronger. What the full post walk adds is the overlayfs rule that a lower must not change while mounted, plus changes to files the command only read; a target-only check would silently drop both, so it is not a speed-up of the same guarantee. (3) inotify/fanotify are not robust: no events for writes through mmap, unprivileged fanotify allows only inode marks (one per directory, like inotify watches, so setting them up is itself a walk), and queues can overflow. The full walk therefore stays; it is syscall-bound (GNU find takes 62 ms against 74 ms for the Python walk on 20k entries), and running it in a thread next to the /tmp copy gained nothing because of the GIL. What was built: lower_changed compares the two maps directly instead of hashing both (fp_post 236 -> 167.5 ms, same check); the git snapshot runs next to the shadow run (wait 0 ms). The snapshot must start after the base walk and end before the post walk; then every entry it reads was stat'ed before and after, so a concurrent change still sets lower_changed. Next to the base walk it would be unsafe, because git could read an entry before the walk stats it; a test pins the order. Fingerprint soundness, probed on WSL2 6.18: on ext4 and tmpfs, 0 of 20,000 same-size in-place rewrites right after a stat kept the fingerprint. Over 20,000 delete-and-recreate cycles, ext4 reused the inode number every time, yet 0 kept the fingerprint. os.utime restores mtime but never ctime. This is Linux 6.13+ multigrain ctime (ext4, xfs, btrfs, tmpfs). Older kernels and other filesystems stamp ctime from a coarse clock tick, so git's racy-entry case applies: an entry whose ctime is within 50 ms of the walk now gets a unique negative ctime and never compares equal, which means rerun or commit conflict, never a silent miss. 9p (/mnt/c) takes its timestamps from the Windows host clock and is already unsupported for workspaces. Result: median fixed cost (prepare + judge) 518.5 -> 377 ms and median added latency 588.5 -> 470 ms with an empty /tmp. The shadow run itself went 66 -> 90.5 ms, because the git snapshot runs next to it. With 5,000 files in /tmp: fixed cost 642 -> 390 ms, added latency 746.5 -> 491.5 ms (C-0011). The two walks are now about 85% of the remaining fixed cost. Revive dir-mtime or notification ideas only if: a change journal exists that also covers mmap writes and needs no walk to set up.
